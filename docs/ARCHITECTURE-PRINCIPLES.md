# فلسفه معماری ریهان (Architecture Philosophy)

**نسخه:** 1.0
**تاریخ:** 2026-08-04
**وضعیت:** تأییدشده (D-059)
**اهمیت:** بحرانی — هر AI یا توسعه‌دهنده جدید MUST بخواند

> هشدار به هوش مصنوعی و توسعه‌دهنده بعدی:
> این سند قانون اساسی معماری ریهان است.
> هر خط کد، هر تصمیم فنی، هر ساختار دیتابیس باید با این سند سازگار باشد.
> اگر در تضاد باشد، کد شما رد می‌شود.

---

## هدف این سند

ریهان باید طوری ساخته شود که:
1. هر قابلیت جدید در آینده بدون بازنویسی اضافه شود
2. هر نیاز جدید بدون اخلال در سیستم فعلی پاسخ داده شود
3. هر تغییر نقطه‌ای و محدود باشد، نه سراسری
4. مقیاس‌پذیری از روز اول در نظر گرفته شود

قانون طلایی:
> امروز کدی بنویس که ۶ ماه دیگر، افزودن قابلیت جدید را آسان کند.

## شش الگوی معماری اجباری

### الگوی ۱: API-First Design
قانون: هر قابلیت ابتدا به‌عنوان API طراحی می‌شود. وب‌سایت فقط یکی از مصرف‌کنندگان API است.

پیاده‌سازی:
- تمام منطق کسب‌وکار در لایه API
- فرانت‌اند فقط مصرف‌کننده API
- هر عملیات = یک endpoint مشخص

مثال عملی:
افزودن اپلیکیشن موبایل در آینده:
→ فقط ساخت یک کلاینت جدید برای همان API
→ بدون تغییر در بک‌اند
→ بدون تغییر در دیتابیس
→ زمان تخمینی: ۲-۳ هفته (نه ۲-۳ ماه)

### الگوی ۲: Internationalization-Ready (i18n)
قانون: تمام متن‌های کاربر در فایل‌های جداگانه ذخیره می‌شوند، نه hardcode در کد.

پیاده‌سازی:
- messages/fa.json برای فارسی
- در آینده: messages/ar.json برای عربی
- حتی اعداد، تاریخ‌ها، و فرمت‌های پولی باید از i18n استفاده کنند
- ساختار URL باید آماده چندزبانه باشد: /fa/product/...

مثال عملی:
افزودن زبان عربی در آینده:
→ ساخت messages/ar.json
→ ترجمه متن‌ها
→ بدون تغییر در کد
→ زمان تخمینی: ۱ هفته (نه ۱ ماه)

### الگوی ۳: Payment Abstraction Layer
قانون: پرداخت به‌عنوان یک لایه جداگانه با interface مشخص طراحی می‌شود.

پیاده‌سازی:
- interface PaymentMethod با متدهای process, verify, refund
- class CardToCardPayment implements PaymentMethod
- در آینده: class OnlineGatewayPayment implements PaymentMethod

مثال عملی:
افزودن درگاه پرداخت آنلاین در آینده:
→ ساخت کلاس جدید OnlineGatewayPayment
→ پیاده‌سازی همان interface
→ بدون تغییر در منطق سفارش
→ زمان تخمینی: ۱ هفته (نه ۲ ماه)

### الگوی ۴: Scalable Database Design
قانون: جداول و شاخص‌ها طوری طراحی می‌شوند که از ۱۰ محصول تا ۱۰,۰۰۰ محصول کار کنند.

پیاده‌سازی:
- شاخص‌گذاری روی فیلدهای جستجو
- استفاده از foreign keys
- جداسازی جداول پرکاربرد
- طراحی برای partitioning در آینده

مثال عملی:
افزایش از ۵۰ محصول به ۵,۰۰۰ محصول:
→ بدون تغییر ساختار جداول
→ فقط افزودن شاخص‌های بیشتر در صورت نیاز
→ زمان تخمینی: ۱ روز (نه ۱ هفته)

### الگوی ۵: Plugin Architecture (Feature Flags)
قانون: هر ماژول به‌صورت مستقل و قابل فعال‌سازی طراحی می‌شود (بر اساس D-023 و D-028).

پیاده‌سازی:
- هر ماژول = یک plugin مستقل
- فعال‌سازی از پنل ادمین
- بدون تغییر کد هسته

مثال عملی:
افزودن ماژول کد تخفیف در آینده:
→ ساخت plugin جدید
→ ثبت در سیستم Feature Flags
→ فعال‌سازی از پنل ادمین
→ بدون تغییر ماژول‌های موجود
→ زمان تخمینی: ۳ روز (نه ۲ هفته)

### الگوی ۶: Content Management Abstraction
قانون: محتوا (داستان، توضیحات، عکس) از کد جدا است.

پیاده‌سازی:
- محتوا در دیتابیس یا فایل‌های جداگانه
- ساختار محتوا قابل ویرایش از پنل ادمین
- بدون hardcode در کد

مثال عملی:
تغییر داستان محصول:
→ از پنل ادمین
→ بدون نیاز به deploy
→ زمان: ۱ دقیقه (نه ۱ ساعت)

## تست‌های الزامی معماری (Architecture Fitness Tests)

برای هر تصمیم فنی جدید، این ۵ تست را انجام دهید:

### تست ۱: تست افزودن اپلیکیشن
اگر ۶ ماه دیگر بخواهیم اپلیکیشن موبایل بسازیم، آیا نیاز به بازنویسی داریم؟
اگر پاسخ بله → معماری نیاز به بازنگری دارد

### تست ۲: تست افزودن زبان
اگر ۶ ماه دیگر بخواهیم زبان عربی اضافه کنیم، چقدر کار دارد؟
اگر بیش از ۱ هفته → معماری نیاز به بازنگری دارد

### تست ۳: تست افزودن درگاه پرداخت
اگر ۶ ماه دیگر بخواهیم درگاه آنلاین اضافه کنیم، آیا باید منطق سفارش را تغییر دهیم؟
اگر پاسخ بله → معماری نیاز به بازنگری دارد

### تست ۴: تست مقیاس‌پذیری
اگر ۶ ماه دیگر ۱۰ برابر محصول داشته باشیم، آیا سیستم کند می‌شود؟
اگر پاسخ بله → معماری نیاز به بازنگری دارد

### تست ۵: تست افزودن ماژول
اگر ۶ ماه دیگر بخواهیم ماژول جدیدی اضافه کنیم، آیا باید کد هسته را تغییر دهیم؟
اگر پاسخ بله → معماری نیاز به بازنگری دارد

## چک‌لیست افزودن قابلیت جدید

هر وقت قابلیت جدیدی اضافه می‌کنید، این چک‌لیست را طی کنید:

- [ ] آیا این قابلیت با ۶ الگوی بالا سازگار است؟
- [ ] آیا این قابلیت ۵ تست بالا را پاس می‌کند؟
- [ ] آیا این قابلیت با VISION-GUARD.md سازگار است؟
- [ ] آیا این قابلیت با PRODUCT-PRINCIPLES.md سازگار است؟
- [ ] آیا این قابلیت به‌صورت plugin مستقل قابل پیاده‌سازی است؟
- [ ] آیا این قابلیت بدون تغییر کد موجود قابل افزودن است؟

اگر پاسخ هر سؤال خیر است، قبل از کدنویسی بازنگری کنید.

## قوانین غیرقابل نقض

### قانون ۱: هیچ hardcode در منطق کسب‌وکار
تمام مقادیر متغیر (قیمت، درصد، تنظیمات) باید از دیتابیس یا فایل config خوانده شوند.

### قانون ۲: هیچ کوئری مستقیم از فرانت‌اند
تمام دسترسی به داده از طریق API انجام می‌شود.

### قانون ۳: هیچ وابستگی مستقیم بین ماژول‌ها
ماژول‌ها فقط از طریق interface یا event با هم ارتباط دارند.

### قانون ۴: هیچ تغییر کد هسته برای ماژول جدید
ماژول‌های جدید به‌عنوان plugin اضافه می‌شوند.

### قانون ۵: هیچ متن hardcode در UI
تمام متن‌ها از i18n خوانده می‌شوند.

### قانون ۶: هیچ پرداخت hardcode
پرداخت فقط از طریق Payment Abstraction Layer انجام می‌شود.

## راهنمای هوش مصنوعی جدید

اگر شما یک هوش مصنوعی جدید هستید که وارد این پروژه می‌شوید:

1. ابتدا این سند را کامل بخوانید
2. سپس AI-ENTRY.md را بخوانید
3. سپس CONTINUITY.md را بخوانید
4. سپس VISION-GUARD.md و PRODUCT-PRINCIPLES.md را بخوانید
5. قبل از نوشتن هر خط کد، ۵ تست معماری را در ذهن خود اجرا کنید
6. اگر تصمیمی با این سند در تضاد است، ابتدا با بنیان‌گذار مشورت کنید

یادتان باشد:
> ریهان یک پروژه ۵ ساله است.
> کدی که امروز می‌نویسید، باید ۵ سال دیگر هم قابل نگهداری باشد.
> سرعت امروز مهم است، اما انعطاف آینده مهم‌تر است.
