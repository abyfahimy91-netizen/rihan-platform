## Patch ۱: الگوی فشرده‌سازی و تبدیل خودکار تصاویر (Media Compression Policy)

### مسئله
داستان محوری (CENTRAL-STORY.md) بر استفاده از عکس‌های باکیفیت و داستان‌محور از محصولات خانوادگی تاکید دارد. اگر تصاویر با کیفیت بالا بدون فشرده‌سازی ذخیره شوند:
- هارد VPS در مدت کوتاهی پر می‌شود
- بکاپ‌های هفتگی (ADR-008) سنگین و پرهزینه می‌شوند
- بارگذاری صفحات در اینترنت ضعیف هوراند کند می‌شود (مغایرت با متمم ADR-003)

### راه‌حل فنی

**کتابخانه:** استفاده از django-imagekit یا Pillow به‌صورت مستقیم در save() method مدل‌ها

**مشخصات فشرده‌سازی:**

| پارامتر | مقدار | دلیل |
| --- | --- | --- |
| فرمت خروجی | **WebP** | ۳۰٪ کوچک‌تر از JPEG با همان کیفیت |
| JPEG Fallback | بله | برای مرورگرهای قدیمی |
| حداکثر عرض | **1200px** | کافی برای نمایش در همه دستگاه‌ها |
| حداکثر ارتفاع | خودکار (نسبت حفظ می‌شود) | |
| کیفیت WebP | 85 | تعادل بین حجم و کیفیت |
| Thumbnail | 300x300 WebP | برای لیست محصولات |
| حذف EXIF | بله | حفظ حریم خصوصی + کاهش حجم |

**نمونه پیاده‌سازی در Django Model:**

از PIL (Pillow) برای تبدیل تصویر اصلی به WebP در save() method استفاده می‌شود.
حداکثر عرض 1200px با حفظ نسبت اعمال می‌شود.
EXIF data برای حفظ حریم خصوصی و کاهش حجم حذف می‌شود.

**اندازه هدف فایل‌ها:**

| نوع | حجم هدف (WebP) |
|------|----------------|
| تصویر محصول (full) | < 150 KB |
| Thumbnail | < 20 KB |
| Banner اصلی | < 200 KB |

**هم‌راستایی:**
- متمم ADR-003: کاهش پهنای باند در اینترنت ضعیف
- ADR-008: کاهش حجم بکاپ‌های هفتگی
- اصل ۱۱: تجربه کاربری سریع‌تر
- ADR-007: lazy loading + srcset با WebP

## Patch ۲: الگوی همگام‌سازی قیمت‌های قدیم در سبد خرید LocalStorage

### مسئله
طبق متمم ADR-003 و ADR-007، سبد خرید تا **۷ روز** در LocalStorage مرورگر کاربر باقی می‌ماند. اگر در این ۷ روز:
- قیمت یک محصول تغییر کند
- موجودی یک محصول کم یا صفر شود
- محصول غیرفعال شود (Feature Flag)

سبد خرید محلی کاربر اطلاعات قدیمی را نشان می‌دهد و در صفحه Checkout با خطای ناخواسته مواجه می‌شود.

### راه‌حل فنی

**اندپوینت جدید در ADR-003:**

POST /api/v1/cart/validate/

**درخواست (از Frontend):**

لیست آیتم‌های سبد خرید با product_id، quantity و local_price

**پاسخ (از Backend):**

- valid: true/false
- changes: لیست تغییرات (price_changed, stock_reduced, out_of_stock, product_disabled, feature_disabled)
- updated_cart: سبد خرید به‌روز شده
- total_price: قیمت کل جدید

**انواع change_type:**

| نوع | توضیح | اقدام |
|-----|-------|-------|
| price_changed | قیمت تغییر کرده | به‌روزرسانی LocalStorage + نمایش پیام |
| stock_reduced | موجودی کم شده | تنظیم quantity یا حذف آیتم |
| out_of_stock | موجودی صفر | حذف آیتم با پیام |
| product_disabled | محصول غیرفعال شده | حذف آیتم |
| feature_disabled | ماژول غیرفعال (ADR-004) | حذف آیتم |

**زمان فراخوانی:**

1. هنگام ورود به صفحه Checkout (اجباری)
2. هنگام بازیابی سبد خرید از LocalStorage در لود اولیه (اگر بیش از ۲۴ ساعت گذشته باشد)
3. قبل از ارسال درخواست پرداخت (آخرین چک)

**پیام‌های کاربر (هم‌راستا با اصل ۱۱):**

- تغییر قیمت: قیمت برخی محصولات در سبد خرید شما به‌روز شد. لطفاً بررسی کنید.
- اتمام موجودی: متاسفانه [نام محصول] در حال حاضر موجود نیست. از سبد خرید شما حذف شد.
- کاهش موجودی: موجودی [نام محصول] کمتر از درخواست شماست. تعداد آن تنظیم شد.

**Rate Limiting:** حداکثر ۲۰ درخواست validate در دقیقه per user/device

**هم‌راستایی:**
- ADR-003: endpoint جدید در API Strategy
- ADR-007: JavaScript برای فراخوانی از LocalStorage
- متمم ADR-003: سازگاری با سبد خرید آفلاین
- اصل ۱۱: شفافیت با کاربر (بدون شگفتی در Checkout)
- ADR-004: بررسی Feature Flag قبل از تأیید

## Patch ۳: مدیریت حجم فایل‌های لاگ (Log Rotation Policy)

### مسئله
در .env.template لاگینگ فعال است. اگر فایل‌های لاگ در Docker Volume بدون سقف حجم رشد کنند:
- هارد سرور پر می‌شود
- کانتینر crash می‌کند
- بکاپ‌های روزانه (ADR-008) سنگین می‌شوند
- لاگ‌های قدیمی بی‌استفاده باقی می‌مانند

### راه‌حل فنی

**استفاده از RotatingFileHandler در Django LOGGING:**

تنظیمات شامل:
- level: INFO
- class: logging.handlers.RotatingFileHandler
- maxBytes: 10 * 1024 * 1024 (۱۰ مگابایت)
- backupCount: 5 (۵ فایل چرخشی)
- formatter: json

دو فایل لاگ:
- /var/log/rihan/app.log (همه لاگ‌ها)
- /var/log/rihan/error.log (فقط خطاها)

**مشخصات:**

| پارامتر | مقدار | دلیل |
| --- | --- | --- |
| maxBytes | **10 MB** | حدود ۱۰۰،۰۰۰ لاگ در هر فایل |
| backupCount | **5** | حداکثر ۶۰ MB لاگ در هر دسته |
| فرمت | JSON | قابل جستجو و تحلیل |
| Rotation trigger | حجم | |

**حجم کل لاگ‌ها:**
- app.log: حداکثر ۶۰ MB (۶ فایل x ۱۰ MB)
- error.log: حداکثر ۶۰ MB
- **مجموع:** ۱۲۰ MB (کمتر از ۰.۵٪ فضای یک VPS ۲۵ GB)

**افزودن به .env.template:**

متغیرهای جدید:
- LOG_LEVEL=INFO
- LOG_MAX_BYTES=10485760
- LOG_BACKUP_COUNT=5
- LOG_DIR=/var/log/rihan

**Docker Volume برای لاگ‌ها:**

logs_volume:/var/log/rihan

**Docker Log Driver (لایه دوم حفاظت):**

در docker-compose.yml:
- driver: json-file
- options: max-size 10m, max-file 5

**هم‌راستایی:**
- ADR-008: تکمیل استراتژی Backup (لاگ‌ها جزو بکاپ نیستند)
- اصل ۱۰: کنترل کامل ادمین روی لاگ‌ها
- امنیت: JSON format برای audit trail
- پایداری: جلوگیری از پر شدن هارد

## Patch ۴: بارگذاری نشان‌های اصالت (Trust Badges) در Seed Data

### مسئله
اسکریپت entrypoint.sh داده‌های دسته‌بندی را بارگذاری می‌کند، اما برای **نشان‌های اصالت و ویژگی‌های بومی هوراند** (موضوع docs/SELECTION-PHILOSOPHY.md) الگوی Fixture مشخص نشده است. این باعث می‌شود:
- در اولین راه‌اندازی، پنل ادمین خالی از نشان‌های اصالت باشد
- بنیان‌گذار مجبور باشد همه را دستی ایجاد کند
- یکپارچگی با داستان محوری حفظ نشود

### راه‌حل فنی

**مدل TrustBadge در ADR-002:**

فیلدها:
- title (CharField, max_length=100)
- description (TextField)
- icon (CharField, max_length=50)
- category (choices: authenticity, family, local, quality)
- is_active (BooleanField)
- display_order (IntegerField)
- created_at (DateTimeField, auto)

**نمونه Trust Badges بومی ریهان:**

1. اصالت خانوادگی - هر محصول توسط خانواده بنیان‌گذار شخصی‌سازی و تأیید می‌شود
2. محصول بومی هوراند - برخی محصولات مستقیماً از هنرمندان و تولیدکنندگان هوراند تأمین می‌شوند
3. بدون واسطه - ارتباط مستقیم با تولیدکننده
4. کیفیت تضمینی - ۵ مرحله کنترل کیفیت
5. بسته‌بندی محترمانه - احترام به شأن مشتری و محیط زیست
6. پشتیبانی ۷ روزه - بازگشت کالا تا ۷ روز

**فایل Fixture: fixtures/trust_badges.json**

شامل ۶ نشان اصالت پیش‌فرض که در اولین راه‌اندازی بارگذاری می‌شوند.

**به‌روزرسانی entrypoint.sh:**

در مرحله ۴ (بارگذاری Seed Data):
- بارگذاری categories.json (اگر وجود داشته باشد)
- بارگذاری trust_badges.json (اگر وجود داشته باشد)
- بارگذاری initial_data.json (اگر وجود داشته باشد)

**هم‌راستایی:**
- SELECTION-PHILOSOPHY.md: فلسفه انتخاب محصول (۵ ستون)
- CENTRAL-STORY.md: داستان اعتماد محلی و خانوادگی
- اصل ۱۱: شفافیت با مشتری
- ADR-002: افزودن مدل TrustBadge به ۱۷ موجودیت (می‌شود ۱۸)
- entrypoint.sh: بارگذاری خودکار
