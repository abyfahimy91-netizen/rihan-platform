## D-039: مدل احراز هویت ریهان

**تاریخ:** 2026-08-02
**فاز:** 3 (اصلاح اسناد فاز 0-1)
**وضعیت:** Superseded by D-040 ❌
**تصمیم‌گیرنده:** عبدالحسین فهیمی

### تصمیم

مدل احراز هویت Hybrid: OTP (Kavenegar) + رمز عبور. از روز اول فعال.

### جزئیات

| موضوع | تصمیم |
|-------|------|
| ثبت‌نام | شماره → OTP (Kavenegar Verify) → تعیین رمز |
| ورود | رمز (پیش‌فرض) یا OTP (جایگزین) |
| فراموشی رمز | خودکار: شماره → OTP → رمز جدید |
| Progressive Registration | نام و آدرس هنگام اولین خرید، نه ثبت‌نام |
| پنل پیامک | Kavenegar — بدون مجوز کسب — فقط کارت ملی |
| هزینه | ~۲۰,۰۰۰ تومان/ماه (سال اول) |
| جلسه | ۳۰ روزه (با «مرا به خاطر بسپار») / ۸ ساعته |
| امنیت | bcrypt(12) + HTTPS + JWT HttpOnly + قفل ۵ بار |
| ورود ادمین | نام کاربری + رمز (بدون OTP) |
| آینده | معماری آماده WebAuthn/Biometric |

### دلیل رد گزینه‌های دیگر

| گزینه | دلیل رد |
|-------|---------|
| OTP بدون رمز (Passwordless) | وابستگی کامل به SMS — اگر نرسد کاربر گیر می‌کند |
| فقط رمز (بدون OTP) | فراموشی رمز — نیاز به تماس با ادمین — غیرخودکار |
| ریست دستی توسط ادمین | غریبه‌ها از هفته اول ممکن است عضو شوند — مقیاس‌پذیر نیست |

### اسناد اصلاح‌شده

- docs/TECHNICAL-REQUIREMENTS.md (بازنویسی کامل — نسخه 2.0)
- docs/USER-STORIES.md — US-011 (ثبت‌نام و ورود)
- docs/USER-FLOWS.md — E2 (بازیابی رمز)

### ارجاعات

- تحقیق: Baymard Institute, NN/g, OWASP, NIST 800-63B
- الگو: دیجی‌کالا (OTP + رمز + فراموشی خودکار)
- اصل حاکم: «انسان اول، فناوری دوم» + «تدریجی، نه انفجاری»

## D-040: مدل نهایی احراز هویت — Passwordless + Device Remembering + Guest Checkout

**تاریخ:** 2026-08-02
**فاز:** 3 (نهایی)
**وضعیت:** تأیید بنیان‌گذار ✅
**تصمیم‌گیرنده:** عبدالحسین فهیمی

### تصمیم نهایی

| موضوع | تصمیم |
|-------|------|
| روش اصلی | Passwordless: شماره موبایل + OTP (Kavenegar) |
| رمز عبور | اختیاری — فقط در تنظیمات حساب |
| Device Remembering | ۳۰ روز — بدون OTP مجدد |
| Guest Checkout | کامل — حداکثر ۵ سفارش مهمان |
| Guest Review | لینک پیامکی + OTP سبک — Token ۷ روزه |
| فراموشی رمز | معنی ندارد (رمز اجباری نیست) |
| ورود ادمین | نام کاربری + رمز (بدون تغییر) |
| پنل پیامک | Kavenegar — ~۲۰,۰۰۰ تومان/ماه |

### دلیل لغو D-039

D-039 مدل Hybrid (رمز اجباری + OTP جایگزین) بود.
مدل Passwordless ساده‌تر، مدرن‌تر، و منطبق با اصل «سادگی» و «انسان اول» است.
Device Remembering مشکل تکرار OTP را حل می‌کند.
Guest Checkout برای دایره اول حیاتی است.

## D-067: مدرک پرداخت کارت‌به‌کارت در MVP

**وضعیت:** تأییدشده ✅  
**فاز:** 4 (Software Planning)

**مرتبط با:** D-003 (شروع با کارت‌به‌کارت), M11 (پرداخت), US-007

### زمینه
کاهش اصطکاک پرداخت برای مشتری ضمن حفظ قدرت تأیید ادمین. حذف کامل رسید ریسک تأیید اشتباه را بالا می‌برد، اما اجباری کردن آن در موبایل آزاردهنده است.

3. **زمان تقریبی واریز** (transfer_time - TIMESTAMP)

### دلایل

### قید مهم
هر سفارش می‌تواند **چندین تلاش پرداخت** داشته باشد (نه فقط یک Payment). UNIQUE(order_id) در جدول Payment حذف می‌شود.

## D-068: مدل تأمین‌کننده در MVP

**تاریخ:** 1405/05/16  
**وضعیت:** تأییدشده ✅  
**فاز:** 4 (Software Planning)  
**سند مرتبط:** decisions/adr/ADR-002-database.md  
**مرتبط با:** D-045 (جریان موجودی), M1 (کاتالوگ), M4 (پنل تأمین‌کننده)

### زمینه
ریهان یک marketplace اعتمادمحور با چند تأمین‌کننده است. باید مشخص شود که آیا هر محصول می‌تواند چند تأمین‌کننده داشته باشد یا خیر.

### تصمیم
**در MVP:** هر محصول دقیقاً یک تأمین‌کننده دارد (Product.supplier_id).
- رابطه: Product N:1 Supplier
- چندتأمین‌کننده در سطح سفارش مجاز است: یک Order می‌تواند OrderItemهایی از Supplierهای مختلف داشته باشد
- این محدودیت MVP است و در آینده اگر نیاز به چندتأمین‌کننده برای یک محصول بود، ADR جدید ثبت می‌شود

### دلایل
- سادگی مدل داده برای MVP
- جلوگیری از پیچیدگی oversell در چند منبع
- هر محصول یک مبدأ مشخص دارد (هم‌راستا با داستان محصول)
- گزارش‌گیری مالی ساده‌تر (هر OrderItem یک supplier_cost دارد)

### پیامدها
- Product.supplier_id NOT NULL
- OrderItem.supplier_id برای گزارش‌گیری مالی
- تأمین‌کننده فقط سفارشات مربوط به محصولات خودش را می‌بیند
