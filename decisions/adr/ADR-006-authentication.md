# ADR-006: احراز هویت Passwordless (OTP + Device Remembering)

| شناسه | ADR-006 |
| --- | --- |
| عنوان | احراز هویت Passwordless (OTP + Device Remembering) |
| وضعیت | **Proposed v2** — اصلاح‌شده بر اساس ۴ الزام اجباری ناظر |
| تاریخ | ۲۰۲۶-۰۸-۰۷ |
| تصمیم‌گیرنده | عبدالحسین فهیمی (بنیان‌گذار) + تحلیلگر فنی |
| مرتبط | D-040, ADR-002, ADR-003, ADR-004, M10, اصل ۹, اصل ۱۰, اصل ۱۱ |

> این سند پیش‌نویس است. تا تصویب ناظر، کد احراز هویت تولید نشود.

## ۱. زمینه و ارجاعات

### چرا Passwordless؟
- **D-040 (مصوب بنیان‌گذار):** احراز هویت با شماره موبایل + OTP، بدون رمز عبور
- **اصل ۱۱ (کرامت مشتری):** کاربر نباید رمز عبور به خاطر بسپارد
- **اصل ۹ (مستقل از خارج):** استفاده از سرویس SMS داخلی (Kavenegar)
- **محدودیت بنیان‌گذار:** غیربرنامه‌نویس، نیاز به ساده‌ترین راه‌حل

### ارجاعات
- D-040: احراز هویت Passwordless (مصوب)
- ADR-002: موجودیت‌های User, DeviceToken, AuditLog
- ADR-003: سه کانال احراز هویت (Web Session / API JWT / Device Token)
- ADR-004: ماژول auth سیستمی است (غیرقابل غیرفعال‌سازی)
- M10: ماژول احراز هویت در MVP-SCOPE

## ۲. جریان احراز هویت اصلی (OTP + Kavenegar)

### مراحل ورود کاربر

**مرحله ۱: درخواست OTP**
- کاربر شماره موبایل خود را وارد می‌کند
- POST /api/v1/auth/otp/request/ با body: { phone: "0912xxxxxxx" }
- سیستم بررسی می‌کند:
  - آیا شماره معتبر است؟ (فرمت ایرانی ۰۹xxxxxxxxx)
  - آیا در Rate Limit نیست؟ (بخش ۴)
  - آیا قفل موقت ندارد؟
- اگر OK:
  - OTP ۶ رقمی تولید می‌شود
  - از طریق Kavenegar Verify ارسال می‌شود
  - OTP در دیتابیس ذخیره می‌شود (hash شده)
  - زمان انقضا: ۲ دقیقه
  - پاسخ: { message: "کد ارسال شد", expires_in: 120 }

**مرحله ۲: تأیید OTP**
- کاربر کد ۶ رقمی را وارد می‌کند
- POST /api/v1/auth/otp/verify/ با body: { phone, otp_code }
- سیستم بررسی می‌کند:
  - آیا OTP معتبر است؟ (hash match)
  - آیا منقضی نشده؟ (۲ دقیقه)
  - آیا تعداد تلاش مجاز باقی است؟ (حداکثر ۳ بار)
- اگر OK:
  - Session/JWT صادر می‌شود (بخش ۵)
  - DeviceToken صادر می‌شود (بخش ۲.۲)
  - AuditLog ثبت می‌شود
  - پاسخ: { token: "...", device_token: "...", user: {...} }
- اگر Not OK:
  - تعداد تلاش افزایش می‌یابد
  - اگر ۳ بار ناموفق: قفل موقت ۳۰ دقیقه
  - پاسخ خطا: { error: "کد نادرست است", attempts_left: N }

**مرحله ۳: ورود مجدد (Device Remembering)**
- اگر کاربر DeviceToken معتبر داشته باشد:
  - نیازی به OTP نیست
  - مستقیم وارد می‌شود
  - DeviceToken هر ۳۰ روز منقضی می‌شود
  - کاربر می‌تواند از پنل دستگاه‌ها را ابطال کند

### مشخصات OTP

| پارامتر | مقدار | دلیل |
| --- | --- | --- |
| طول کد | ۶ رقم | استاندارد صنعتی |
| طول عمر | ۲ دقیقه | امنیت + UX |
| تعداد تلاش | ۳ بار در ۱۰ دقیقه | جلوگیری از brute-force |
| قفل موقت | ۳۰ دقیقه | پس از ۳ تلاش ناموفق |
| ذخیره‌سازی | hash (bcrypt) | امنیت داده |
| ارسال | Kavenegar Verify | سرویس داخلی ایران |

### مشخصات DeviceToken

| پارامتر | مقدار | دلیل |
| --- | --- | --- |
| طول عمر | ۳۰ روز | D-040 |
| فرمت | UUID v4 | استاندارد |
| ذخیره‌سازی | دیتابیس (جدول DeviceToken) | ADR-002 |
| ابطال | از پنل کاربر + پنل ادمین | اصل ۱۰ |
| محدودیت | حداکثر ۵ دستگاه per کاربر | امنیت |

## ۳. Guest Checkout (هم‌راستا با ADR-002)

### اصول
- مهمان می‌تواند بدون ثبت‌نام سفارش دهد
- سقف: ۵ سفارش مهمان per device
- پس از ۵ سفارش: الزام به ثبت‌نام
- Guest Review با توکن محدود (بدون ورود کامل)

### جریان Guest Checkout

**مرحله ۱: افزودن به سبد**
- مهمان بدون ورود محصول را به سبد اضافه می‌کند
- Session موقت صادر می‌شود (guest_session_id)
- هیچ اطلاعات شخصی ذخیره نمی‌شود

**مرحله ۲: تکمیل سفارش**
- مهمان اطلاعات تماس را وارد می‌کند:
  - نام و نام خانوادگی
  - شماره موبایل (برای پیگیری)
  - آدرس تحویل
- سفارش با guest_phone ثبت می‌شود
- هیچ حساب کاربری ساخته نمی‌شود

**مرحله ۳: تبدیل Guest به کاربر (اختیاری)**
- پس از تکمیل سفارش، پیشنهاد ثبت‌نام داده می‌شود
- اگر پذیرفت:
  - OTP به شماره موبایل ارسال می‌شود
  - حساب کاربری ساخته می‌شود
  - سفارش‌های قبلی به حساب لینک می‌شوند
- اگر نپذیرفت:
  - سفارش با guest_phone باقی می‌ماند
  - پیگیری از طریق شماره موبایل

### Guest Review (توکن محدود)

- مهمان می‌تواند بدون ورود نظر بدهد
- توکن محدود صادر می‌شود (guest_review_token)
- طول عمر توکن: ۷ روز
- فقط برای ویرایش/حذف نظر خودش
- بدون دسترسی به سایر بخش‌ها

### قوانین Guest

| قانون | مقدار | دلیل |
| --- | --- | --- |
| سقف سفارش مهمان | ۵ per device | جلوگیری از سوءاستفاده |
| الزام ثبت‌نام | پس از ۵ سفارش | تبدیل به کاربر |
| Guest Review | توکن ۷ روزه | UX بدون امنیت کامل |
| ذخیره اطلاعات | فقط در Order | حریم خصوصی |


## ۴. Rate Limiting و ضدسوءاستفاده

### محدودیت‌های درخواست OTP

| پارامتر | محدودیت | دلیل |
| --- | --- | --- |
| درخواست OTP per شماره | ۳ بار در ۱۰ دقیقه | جلوگیری از SMS bombing |
| درخواست OTP per IP | ۱۰ بار در ساعت | جلوگیری از حمله توزیع‌شده |
| تأیید OTP per شماره | ۳ بار در ۱۰ دقیقه | جلوگیری از brute-force |
| قفل موقت | ۳۰ دقیقه | پس از ۳ تلاش ناموفق |
| قفل سخت | ۲۴ ساعت | پس از ۵ قفل موقت متوالی |

### محافظت در برابر حملات

**SMS Bombing:**
- محدودیت per شماره + per IP
- CAPTCHA پس از ۲ درخواست متوالی
- تأخیر تدریجی (exponential backoff)

**Brute-Force:**
- حداکثر ۳ تلاش برای OTP
- قفل موقت ۳۰ دقیقه
- لاگ کامل در AuditLog

**Account Enumeration:**
- پیام خطای یکسان برای شماره وجود ندارد / OTP نادرست
- عدم افشای اطلاعات در پاسخ API

### لاگ‌های امنیتی

تمام رویدادهای احراز هویت در AuditLog ثبت می‌شوند:
- درخواست OTP (شماره، IP، زمان)
- تأیید OTP (موفق/ناموفق)
- ورود موفق (device, IP, user agent)
- قفل موقت/سخت
- ابطال DeviceToken

**دسترسی به لاگ‌ها:**
- ادمین: مشاهده کامل در پنل
- بنیان‌گذار: گزارش هفتگی خودکار
- retention: حداقل ۱ سال (اصل ۱۰)

## ۵. Session/Token Strategy (هم‌راستا با ADR-003)

### سه کانال احراز هویت (ADR-003)

**کانال ۱: Web (مرورگر)**
- روش: Session cookie
- ویژگی: HttpOnly, Secure, SameSite=Strict
- طول عمر: ۳۰ روز (با تمدید خودکار)
- استفاده: تمام درخواست‌های HTMX و Template

**کانال ۲: API (اپ موبایل آینده)**
- روش: JWT در Authorization header
- ویژگی: Stateless، قابل ابطال
- طول عمر Access Token: ۱۵ دقیقه
- طول عمر Refresh Token: ۳۰ روز
- استفاده: فقط /api/v1/ از اپ موبایل
- **نکته:** در MVP فعال نمی‌شود

**کانال ۳: Device Remembering (D-040)**
- روش: DeviceToken جداگانه
- ویژگی: بلندمدت (۳۰ روز)، قابل ابطال
- استفاده: حذف نیاز به OTP مجدد برای دستگاه شناخته‌شده
- محدودیت: حداکثر ۵ دستگاه per کاربر

### قوانین کلی

- **هرگز JWT را هم در Header و هم در Cookie نفرستید** — فقط یکی بسته به کانال
- **Session/JWT فقط پس از تأیید OTP صادر می‌شود**
- **DeviceToken جدا از Session/JWT است** و برای ورود مجدد استفاده می‌شود
- **ابطال فوری:** کاربر می‌تواند از پنل تمام دستگاه‌ها را ابطال کند

### Refresh Strategy و الگوریتم‌های امنیتی

**Refresh Token Rotation (RTR):**
- در هر بار تمدید نشست (استفاده از Refresh Token)، توکن قبلی فوراً باطل (Invalidate) شده و یک Refresh Token جدید صادر می‌شود.
- **محافظت در برابر سرقت:** اگر یک Refresh Token سرقت‌شده و قبل از توکن اصلی استفاده شود، سیستم متوجه استفاده مجدد (Reuse) از توکن باطل‌شده شده و تمام نشست‌های فعال آن کاربر را به‌صورت خودکار باطل می‌کند (Revoke All).

**ابطال سراسری نشست‌ها (Revoke All Active Sessions / Remote Logout):**
- **کاربر:** از طریق پنل کاربری > امنیت، دکمه «خروج از تمام دستگاه‌ها» تمام Sessionها، JWTها و DeviceTokenهای فعال را باطل می‌کند.
- **ادمین:** از طریق پنل ادمین، در صورت مشاهده رفتار مشکوک، می‌تواند تمام نشست‌های یک کاربر خاص را به‌صورت سراسری باطل کند (Remote Logout).

**Web Session:**
- تمدید خودکار با هر درخواست (sliding window)
- انقضا: ۳۰ روز بدون فعالیت

**API JWT (آینده):**
- Access Token: ۱۵ دقیقه
- Refresh Token: ۳۰ روز
- Refresh با POST /api/v1/auth/refresh/ (با الزام RTR)

**DeviceToken:**
- انقضا: ۳۰ روز از آخرین استفاده
- تمدید خودکار با هر ورود موفق

## ۶. اصل ۹ (مستقل از خارج)

### توجیه استفاده از Kavenegar

**چرا Kavenegar؟**
- سرویس SMS داخلی ایران (مستقل از خارج)
- بدون نیاز به حساب ارزی یا کارت اعتباری خارجی
- پشتیبانی فارسی
- API ساده و مستند
- قابلیت Verify (OTP آماده)

**چرا نه سرویس‌های خارجی؟**
- Twilio, Vonage: نیاز به حساب ارزی
- Firebase Auth: وابستگی به Google
- Auth0: وابستگی به سرویس خارجی
- **اصل ۹:** استقلال از سرویس‌های خارج از ایران

### Fallback و مدل ترکیبی (Hybrid Auth)

**سطح ۱: درگاه پیامکی ثانویه و تماس صوتی (خودکار)**
- Interface مشترک SmsProvider (Strategy Pattern)
- Provider پیش‌فرض: Kavenegar
- Provider ثانویه: فرازاس‌ام‌اس، اس‌ام‌اس.آی‌آر یا ملی‌پیامک (در صورت عدم تحویل پیامک ظرف ۶۰ ثانیه، به‌صورت خودکار روی Provider ثانویه سوئیچ می‌شود).
- **Voice OTP (تماس صوتی خودکار):** در صورت عدم تحویل پیامک پس از ۶۰ ثانیه و تلاش مجدد کاربر، سیستم به‌صورت خودکار تماس صوتی خودکار برای دیکته کردن کد OTP برقرار می‌کند.
- **حذف کامل ManualSmsProvider:** ارسال دستی پیامک توسط ادمین به دلیل غیرعملیاتی بودن و مغایرت با اصل اتوماسیون، کاملاً حذف می‌شود.

**سطح ۲: مدل ترکیبی (Hybrid Auth) با رمز عبور پشتیبان اختیاری**
- **روش پیش‌فرض:** ثبت‌نام و ورود با OTP پیامکی (حفظ سادگی برای پرسوناهای هوراند و کاربران غیرفنی).
- **رمز عبور پشتیبان اختیاری:** کاربر پس از ورود موفق، می‌تواند در پنل کاربری خود یک «رمز عبور پشتیبان» تعریف کند.
- **فرم ورود:** گزینه «ورود با رمز عبور پشتیبان» تعبیه می‌شود. در صورت قطعی کامل درگاه‌های پیامک و تماس صوتی، کاربر می‌تواند با شماره موبایل + رمز عبور پشتیبان وارد شود.
- **امنیت رمز پشتیبان:** با bcrypt hash شده، پس از ۵ بار تلاش ناموفق قفل می‌شود، و فقط از طریق OTP پیامکی قابل بازیابی است.

### عدم وابستگی به سرویس‌های خارجی دیگر

- **احراز هویت:** فقط Kavenegar (داخلی)
- **ذخیره‌سازی:** سرور خودمیزبان (D-022)
- **دیتابیس:** PostgreSQL روی سرور خودی
- **Cache:** in-process/local (ADR-004)
- **هیچ وابستگی به AWS, Azure, Google Cloud نیست**


## ۷. اصل ۱۰ (کنترل کامل ادمین)

### پارامترهای قابل تنظیم از پنل ادمین

| پارامتر | مقدار پیش‌فرض | قابل تغییر |
| --- | --- | --- |
| طول عمر OTP | ۲ دقیقه | بله (۱ تا ۵ دقیقه) |
| تعداد تلاش مجاز | ۳ بار | بله (۱ تا ۵ بار) |
| قفل موقت | ۳۰ دقیقه | بله (۱۰ تا ۶۰ دقیقه) |
| Device Remembering | ۳۰ روز | بله (۷ تا ۹۰ روز) |
| سقف سفارش مهمان | ۵ سفارش | بله (۱ تا ۱۰) |
| Rate Limit OTP per شماره | ۳ بار در ۱۰ دقیقه | بله |
| Rate Limit OTP per IP | ۱۰ بار در ساعت | بله |

**نکته:** تغییرات در AuditLog ثبت می‌شوند (چه کسی، چه زمانی، از چه به چه).

### مشاهده و مدیریت نشست‌ها

**پنل ادمین - بخش احراز هویت:**
- لیست تمام کاربران با وضعیت ورود
- لیست DeviceTokenهای فعال per کاربر
- مشاهده IP، user agent، زمان آخرین ورود
- **ابطال دستی:** ادمین می‌تواند هر DeviceToken یا Session را ابطال کند
- **قفل دستی:** ادمین می‌تواند یک کاربر را موقتاً قفل کند

**پنل کاربر - بخش امنیت:**
- لیست دستگاه‌های واردشده
- زمان و IP آخرین ورود
- **ابطال خودکار:** کاربر می‌تواند دستگاه‌های خودش را ابطال کند
- **خروج از همه دستگاه‌ها:** یک کلیک برای ابطال همه

### لاگ کامل بدون حذف

- تمام رویدادهای احراز هویت در AuditLog ثبت می‌شوند
- **Retention:** حداقل ۱ سال (قابل افزایش از پنل ادمین)
- **عدم حذف:** هیچ لاگی توسط کاربر یا ادمین قابل حذف نیست
- **دسترسی:** فقط ادمین و بنیان‌گذار
- **گزارش‌دهی:** گزارش هفتگی خودکار به بنیان‌گذار

## ۸. اصل ۱۱ (کرامت مشتری)

### شفافیت در استفاده از داده

**در فرم ورود:**
- پیام واضح: "شماره موبایل شما فقط برای احراز هویت استفاده می‌شود"
- لینک به سیاست حریم خصوصی
- عدم استفاده از dark patterns (چک‌باکس‌های پنهان، دکمه‌های گمراه‌کننده)

**در فرم Guest Checkout:**
- پیام واضح: "اطلاعات شما فقط برای پیگیری سفارش استفاده می‌شود"
- گزینه ثبت‌نام اختیاری (نه اجباری)
- عدم ارسال ایمیل/SMS تبلیغاتی بدون اجازه

### حق فراموش‌شدن (تفکیک PII و سوابق مالی)

- کاربر می‌تواند درخواست حذف حساب بدهد
- **مهلت گمنام‌سازی (Anonymization):** حداکثر ۷ روز پس از درخواست
- **گمنام‌سازی PII (داده‌های شخصی):**
  - شماره موبایل، نام، آدرس و ایمیل از دیتابیس کاربران حذف یا با `anonymous_user_id` جایگزین می‌شوند.
  - DeviceTokenها و Sessionها فوراً باطل و حذف می‌شوند.
- **نگهداری دفاتر مالی (Financial Ledger Retention):**
  - طبق قوانین تجارت الکترونیک و حسابداری ایران، سوابق فاکتورها و تراکنش‌های مالی باید حداقل ۳ تا ۵ سال نگهداری شوند.
  - سوابق سفارش‌ها و پرداخت‌ها در دیتابیس باقی می‌مانند، اما به جای `user_id` به `anonymous_user_id` لینک می‌شوند (هیچ راهی برای ردیابی هویت واقعی فرد از روی فاکتور وجود نخواهد داشت).
  - AuditLog برای امنیت و حسابرسی حفظ می‌شود.
- **اطلاع‌رسانی:** کاربر قبل از حذف، لیست داده‌های گمنام‌شده و سوابق مالی نگهداری‌شده را به شفافیت می‌بیند.

### پیام‌های خطای محترمانه

**بدون:**
- "شماره اشتباه است" (ممکن است حساب وجود نداشته باشد)
- "کاربر وجود ندارد" (account enumeration)
- پیام‌های فنی یا انگلیسی

**با:**
- "کد ارسال‌شده نادرست است. لطفاً دوباره تلاش کنید."
- "کد منقضی شده است. لطفاً کد جدید دریافت کنید."
- "به دلیل تلاش‌های متعدد، حساب شما موقتاً قفل شده است. لطفاً ۳۰ دقیقه صبر کنید."
- "در صورت مشکل، با پشتیبانی تماس بگیرید."

### عدم استفاده از Dark Patterns

- **ممنوع:** چک‌باکس‌های از پیش انتخاب‌شده برای تبلیغات
- **ممنوع:** دکمه‌های گمراه‌کننده (مثلاً "ادامه" به جای "خروج")
- **ممنوع:** اجبار به ثبت‌نام برای مشاهده محصول
- **ممنوع:** پنهان‌کردن گزینه خروج یا حذف حساب
- **مجاز:** پیشنهاد ثبت‌نام پس از سفارش (با گزینه رد واضح)

## ۹. امنیت و حریم خصوصی

### ذخیره‌سازی امن

**شماره موبایل:**
- ذخیره به‌صورت hash (bcrypt) برای جستجو
- ذخیره به‌صورت encrypted (AES-256) برای نمایش در پنل ادمین
- **هرگز** به‌صورت plaintext ذخیره نمی‌شود

**OTP:**
- hash شده (bcrypt) در دیتابیس
- انقضا خودکار پس از ۲ دقیقه
- حذف از دیتابیس پس از تأیید یا انقضا

**DeviceToken:**
- hash شده در دیتابیس
- فقط hash در دیتابیس، token اصلی یک‌بار به کاربر نمایش داده می‌شود
- ابطال فوری از پنل کاربر/ادمین

**Session/JWT:**
- HttpOnly cookie (برای وب)
- Secure flag (فقط HTTPS)
- SameSite=Strict (جلوگیری از CSRF)

### الزامات OWASP

- **OWASP ASVS Level 1:** حداقل الزامات برای MVP
- **OWASP Top 10:** پوشش کامل در طراحی
  - A01 Broken Access Control → RBAC (ADR-002)
  - A02 Cryptographic Failures → hash/encryption
  - A03 Injection → parameterized queries (Django ORM)
  - A04 Insecure Design → Rate Limiting
  - A07 Authentication Failures → Passwordless + OTP
  - A09 Logging Failures → AuditLog کامل

### آمادگی برای آینده (Passkey/WebAuthn)

- **در MVP اجرا نمی‌شود**
- اما معماری آماده است:
  - Interface مشترک AuthProvider
  - پیاده‌سازی فعلی: SmsOtpProvider
  - پیاده‌سازی آینده: WebAuthnProvider
- افزودن Passkey بدون بازنویسی هسته (مشابه ADR-005 Payment Gateway)

### حریم خصوصی شماره موبایل

- **اصل اعتماد محلی (CENTRAL-STORY.md):** شماره موبایل مشتری امانت است
- **عدم اشتراک‌گذاری:** شماره موبایل هرگز به تأمین‌کننده یا شخص ثالث داده نمی‌شود
- **دسترسی محدود:** فقط ادمین و بنیان‌گذار می‌توانند شماره کامل را ببینند
- **نمایش محدود:** در UI فقط ۴ رقم آخر نمایش داده می‌شود (مثلاً ۰۹۱۲***۷۸۹۰)
- **لاگ‌ها:** در AuditLog فقط hash شماره ذخیره می‌شود، نه خود شماره

### شفاف‌سازی لایه Middleware (هم‌راستا با ADR-003 و ADR-004)

**یکپارچگی با API Gateway (ADR-003):**
- یک Middleware اختصاصی در Django (مثلاً `AuthenticationMiddleware`) قبل از رسیدن درخواست به View اجرا می‌شود.
- **استخراج توکن:** این Middleware هدر `Authorization: Bearer <token>` را برای درخواست‌های API استخراج می‌کند، یا کوکی `sessionid` را برای درخواست‌های وب می‌خواند.
- **اعتبارسنجی:** توکن استخراج‌شده اعتبارسنجی شده و در صورت موفقیت، `request.user` و `request.auth` جمع‌آوری می‌شود. در صورت عدم اعتبار، درخواست با خطای 401 رد می‌شود.

**یکپارچگی با Feature Flags (ADR-004):**
- Middleware دوم (`FeatureFlagMiddleware`) پس از احراز هویت و قبل از اجرای منطق View اجرا می‌شود.
- این Middleware مسیر درخواست (URL) را بررسی کرده و `module_key` مرتبط را استخراج می‌کند.
- اگر Feature Flag آن ماژول در وضعیت غیرفعال باشد، Middleware قبل از رسیدن به View یا اجرای هرگونه منطق احراز هویت پیچیده، درخواست را با کد 404 یا 503 رد می‌کند. این کار از بار اضافی روی سرور جلوگیری کرده و امنیت را افزایش می‌دهد.

## ۱۱. Out of Scope صریح

### در MVP اجرا نمی‌شود

- **رمز عبور:** Passwordless فقط، هیچ رمز عبوری وجود ندارد
- **ورود با ایمیل:** فقط شماره موبایل
- **ورود با شبکه‌های اجتماعی:** Google, Facebook, Twitter
- **Two-Factor Authentication (2FA):** OTP خودش یک عامل است
- **Passkey/WebAuthn:** فقط معماری آماده، اجرا در آینده
- **ورود با biometrics:** اثر انگشت، Face ID
- **Multi-language OTP messages:** فقط فارسی در MVP
- **Voice OTP:** فقط SMS
- **WhatsApp OTP:** فقط SMS

### مرز دقیق MVP

- فقط OTP پیامکی با Kavenegar
- Device Remembering ۳۰ روزه
- Guest Checkout با سقف ۵ سفارش
- Rate Limiting کامل
- AuditLog کامل
- بدون هیچ integration خارجی دیگر
