## ۱. زمینه و ضرورت

### ۱.۱ مشکل شناسایی‌شده

پس از بررسی کامل پروژه از فاز ۰ تا فاز ۴، مشخص شد که ایده اصلی بنیان‌گذار در طول فازهای مختلف کمرنگ شده است. بنیان‌گذار در CENTRAL-STORY.md به صراحت گفته است:

> «یک وب‌سایت حرفه‌ای و باکلاس. نه اینستاگرام‌شاپ. نه واتساپ‌بازی. یک سایت شیک که قیمت مشخص است، لینک را می‌فرستی، طرف سفارش می‌دهد. بدون مکالمه خجالت‌آور. حرفه‌ای و در شأن یک کارمند دولت.»

و:

> «لوکس. مدرن. باوقار. با شخصیت. نه اینستاگرام‌بازی. نه سلفی. نه فیلم‌بازی. نه خودنمایی. نه هیاهو. نه برندسازی شخصی. **یک برند بی‌نام ولی با اعتبار.**»

### ۱.۲ انحرافات شناسایی‌شده

| انحراف | توضیح |
|--------|--------|
| D-074 (Micro-MVP) | ۸ ماژول حیاتی حذف شدند، پنل خانواده و تأمین‌کننده حذف شدند |

### ۱.۳ ضرورت بازنگری

بنیان‌گذار تأیید کرده است که:
1. پروژه باید **کامل** باشد، نه ناقص
2. زمان‌بندی مهم نیست (وایب‌کدینگ)
3. سایت باید **فاخر، آبرومند، بدون اینستاگرام‌بازی** باشد
4. سایت باید **بفروشد** ولی **بدون برندسازی شخصی**
5. غریبه‌ها نباید بدانند چه کسی پشت سایت است
6. حفظ **حیای بنیان‌گذار و عزت نفس** ضروری است
7. پروژه باید **ماژولار و پلاگین‌محور** باشد و به راحتی قابل توسعه آینده باشد

### تصمیم ۲: برند مستقل (Business Brand) — بدون برندسازی شخصی

**زمینه:**
بنیان‌گذار می‌خواهد سایت بدون اشاره به هویت شخصی او باشد. غریبه‌ها نباید بدانند چه کسی پشت سایت است. اما اطرافیان می‌توانند بدانند و به دیگران بگویند «مورد تأیید است».

**تصمیم:**

#### ۲.۱ قوانین برند مستقل

| قانون | توضیح |
|-------|--------|
| **بدون نام بنیان‌گذار در صفحات عمومی** | نام «عبدالحسین فهیمی» در هیچ صفحه عمومی سایت نباشد |
| **بدون عکس بنیان‌گذار در صفحات عمومی** | عکس بنیان‌گذار در هیچ صفحه عمومی سایت نباشد |
| **بدون داستان شخصی بنیان‌گذار در صفحات عمومی** | داستان شخصی بنیان‌گذار در هیچ صفحه عمومی سایت نباشد |
| **فقط هویت برند «ریهان»** | هویت بصری فقط «ریهان» باشد |
| **صفحه درباره فقط داستان برند** | صفحه درباره فقط داستان برند (نه داستان شخصی بنیان‌گذار) |
| **در پنل ادمین نام بنیان‌گذار باشد** | در پنل ادمین نام شما و همسرتان باشد، اما در سایت عمومی نباشد |

#### ۲.۲ تعریف داستان برند برای صفحه درباره

صفحه درباره باید شامل:
- داستان برند ریهان (نه داستان شخصی بنیان‌گذار)
- مأموریت برند
- ارزش‌های برند
- تعهد به مشتری
- بدون اشاره به نام، عکس یا هویت شخصی بنیان‌گذار

### تصمیم ۳: صفحه محصول متمایز و بلوک‌محور (Block-based Product Storytelling)

**زمینه:**
صفحه محصول باید:
- متمایز از فروشگاه‌های معمولی باشد
- روایت‌محور، لوکس و باوقار باشد
- بدون اینستاگرام‌بازی باشد
- **به ادمین اختیار کامل برای روایت‌گری بدهد** (نه فقط پر کردن فیلدها)

**تصمیم:**

#### ۳.۱ سیستم بلوک‌محور

ادمین می‌تواند با استفاده از بلوک‌های زیر، روایت کامل هر محصول را بسازد:

| نوع بلوک | توضیح | فیلدها |
|----------|--------|--------|
| **text** | متن آزاد | content (Rich Text) |
| **heading** | عنوان | text, level (H2/H3/H4) |
| **image** | عکس | image, alt_text, caption, width |
| **gallery** | گالری عکس | images[], columns (2/3/4) |
| **video** | ویدیو | video_file یا video_url, poster, caption |
| **link** | لینک | text, url, target |
| **quote** | نقل قول | quote, author |
| **table** | جدول | rows[], header_row |
| **spacer** | فاصله‌گذار | height (small/medium/large) |
| **cta** | دکمه اقدام | text, action |
| **trust_badges** | Trust Badges | badges[] |
| **related_products** | محصولات مرتبط | products[], max_count |

#### ۳.۲ قابلیت‌های ادمین

| قابلیت | توضیح |
|--------|--------|
| افزودن بلوک | ادمین می‌تواند بلوک جدید اضافه کند |
| حذف بلوک | ادمین می‌تواند بلوک را حذف کند |
| ویرایش بلوک | ادمین می‌تواند بلوک را ویرایش کند |
| تغییر ترتیب | ادمین می‌تواند ترتیب بلوک‌ها را تغییر دهد (drag & drop) |
| فعال/غیرفعال | ادمین می‌تواند بلوک را فعال/غیرفعال کند |
| پیش‌نمایش | ادمین می‌تواند قبل از انتشار پیش‌نمایش ببیند |
| افزودن لینک در متن | ادمین در متن آزاد لینک بگذارد |
| افزودن عکس در هر جا | ادمین در هر جای روایت عکس بگذارد |
| افزودن ویدیو | ادمین ویدیو آپلود کند یا لینک بدهد |

#### ۳.۳ قوانین طراحی صفحه محصول

| قانون | توضیح |
|-------|--------|
| **مینیمال** | طراحی ساده، بدون شلوغ‌کاری |
| **باوقار** | فونت‌ها، رنگ‌ها و تصاویر باوقار |
| **بدون اینستاگرام‌بازی** | بدون emoji زیاد، فونت‌های شلوغ، رنگ‌های جیغ |
| **بدون countdown timer** | بدون تایمر شمارش معکوس |
| **بدون "فقط X عدد باقی مانده"** | مگر واقعاً کم باشد |
| **بدون popup‌های مزاحم** | بدون popup‌های مزاحم |
| **CTA باوقار** | دکمه افزودن به سبد باوقار، نه پرخاشگر |

#### ۳.۴ مثال: روایت سماق هوراند

ادمین می‌تواند این بلوک‌ها را به ترتیب اضافه کند:

1. **heading (H2):** «سماق هوراند»
2. **text:** «سماق هوراند از مزارع کوهستانی هوراند جمع‌آوری می‌شود...»
3. **image:** عکس مزارع هوراند
4. **text:** «این سماق به دلیل آب‌وهوای خاص منطقه، طعمی منحصربه‌فرد دارد...»
5. **video:** ویدیوی جمع‌آوری سماق
6. **quote:** «بهترین سماقی که تا حالا خوردم» — مشتری ریهان
7. **table:** مشخصات فنی (وزن، بسته‌بندی، تاریخ انقضا)
8. **cta:** «افزودن به سبد»

### تصمیم ۴: قیف فروش (Sales Funnel) — تبدیل بازدیدکننده به خریدار

**زمینه:**
سایت باید بفروشد. بازدیدکننده باید تبدیل به خریدار شود. بدون قیف فروش، سایت نمی‌تواند بفروشد.

**تصمیم:**

#### ۴.۱ تعریف قیف فروش

| مرحله | نام | هدف | استراتژی |
|-------|-----|-----|----------|
| ۱ | **آگاهی (Awareness)** | بازدیدکننده سایت را بشناسد | سئو + محتوای صفحه درباره |
| ۲ | **علاقه‌مندی (Interest)** | بازدیدکننده به محصول علاقه‌مند شود | داستان محصول + روایت‌سازی |
| ۳ | **تصمیم‌گیری (Decision)** | بازدیدکننده تصمیم به خرید بگیرد | Trust Badges + نظرات + گارانتی |
| ۴ | **اقدام (Action)** | بازدیدکننده خرید کند | سبد خرید ساده + پرداخت کارت‌به‌کارت |
| ۵ | **وفاداری (Loyalty)** | خریدار دوباره خرید کند | پیامک پس از تحویل + دعوت به نظر |

#### ۴.۲ استراتژی تبدیل برای هر مرحله

| مرحله | استراتژی تبدیل |
|-------|----------------|
| آگاهی | سئو محلی (هوراند، تبریز، تهران) + محتوای صفحه درباره |
| علاقه‌مندی | داستان محصول + عکس‌های حرفه‌ای + روایت‌سازی |
| تصمیم‌گیری | Trust Badges + نظرات تأییدشده + گارانتی مرجوعی |
| اقدام | سبد خرید ساده (حداکثر ۳ مرحله) + پرداخت کارت‌به‌کارت |
| وفاداری | پیامک پس از تحویل + دعوت به نظر + تخفیف برای خرید مجدد |

#### ۴.۳ هدف نرخ تبدیل

- میانگین نرخ تبدیل فروشگاه‌های ایرانی: ۱-۳٪
- هدف ریهان: **۳٪** (بالاتر از میانگین ایران)
- دلیل: اعتمادمحور بودن برند + روایت‌سازی + Trust Badges

### تصمیم ۸: معماری پلاگین‌محور کامل (Plugin Architecture)

**زمینه:**
پروژه باید ماژولار و پلاگین‌محور باشد. هر ماژول و هر بلوک باید مستقل باشد و بدون تغییر کد هسته قابل افزودن باشد. این اصل برای توسعه آینده حیاتی است.

**تصمیم:**

#### ۸.۱ معماری پلاگین‌محور برای ماژول‌ها

| ویژگی | توضیح |
|-------|--------|
| هر ماژول مستقل است | هر ماژول کد، دیتابیس و API جداگانه دارد |
| Feature Flag برای هر ماژول | هر ماژول از پنل ادمین قابل فعال/غیرفعال است |
| افزودن ماژول جدید بدون تغییر کد هسته | فقط یک پوشه جدید در src/modules/ اضافه می‌شود |
| حذف ماژول بدون تأثیر بر سایر ماژول‌ها | غیرفعال‌سازی یک ماژول، سایر ماژول‌ها را تحت تأثیر قرار نمی‌دهد |
| Hook System | هر ماژول می‌تواند به رویدادهای سیستم گوش دهد |
| Migration مستقل | هر ماژول migration دیتابیس خودش را دارد |

#### ۸.۲ معماری پلاگین‌محور برای بلوک‌ها

| ویژگی | توضیح |
|-------|--------|
| هر بلوک مستقل است | هر بلوک کد و قالب جداگانه دارد |
| افزودن بلوک جدید بدون تغییر کد هسته | فقط یک پوشه جدید در src/blocks/ اضافه می‌شود |
| حذف بلوک بدون تأثیر بر سایر بلوک‌ها | حذف یک بلوک، سایر بلوک‌ها را تحت تأثیر قرار نمی‌دهد |
| Feature Flag برای هر بلوک | هر بلوک از پنل ادمین قابل فعال/غیرفعال است |
| Interface مشترک | همه بلوک‌ها یک interface مشترک دارند |
